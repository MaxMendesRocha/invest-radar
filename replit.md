# InvestRadar

Agente de gestão de carteira de investimentos: monitora ativos (ações, FIIs, ETFs, BDRs, fundos, renda fixa), gera score/análise por ativo, alertas do "Radar Inteligente" e oportunidades, com base no prompt em `attached_assets/Prompt_Agente_Gestao_Carteira_Investimentos_*.md`.

## Run & Operate

Local (fora do Replit):

- Suba um Postgres local e crie um banco (ex: `invest_radar`).
- `DATABASE_URL="postgresql://user:pass@127.0.0.1:5432/invest_radar" pnpm --filter @workspace/db run push` — cria/atualiza o schema
- `DATABASE_URL=... pnpm --filter @workspace/scripts run seed-opportunities` — popula a lista curada de Oportunidades (apaga e recria)
- `DATABASE_URL=... SESSION_SECRET=<qualquer-string> PORT=8080 pnpm --filter @workspace/api-server run dev` — API (build + start)
- `PORT=25214 BASE_PATH=/ pnpm --filter @workspace/carteira run dev` — frontend (Vite, com proxy `/api` → `http://localhost:8080`, configurável via `API_PROXY_TARGET`)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- Required env: `DATABASE_URL`, `SESSION_SECRET` (api-server), `PORT`/`BASE_PATH` (ambos os artifacts)
- Env opcional: `BRAPI_TOKEN` (api-server) — token gratuito em https://brapi.dev/dashboard. Sem ele, só PETR4/VALE3/ITUB4/MGLU3 retornam cotação real; os demais tickers caem no fallback (preço médio de compra). Free tier: 15.000 requisições/mês.
- Env opcional: `ANTHROPIC_API_KEY` (api-server) — gerada em https://console.anthropic.com, paga por uso (não é a mesma chave/assinatura do Claude). Sem ela, o Radar de Notícias mostra as manchetes reais sem classificação de impacto (`impact: null`); com ela, cada manchete é classificada via Claude Haiku, a recomendação de monitoramento por ativo e o diagnóstico de saúde da carteira ganham síntese via IA, e as oportunidades regeneradas ganham texto reescrito — em todos os casos, sem a chave cai no texto/fallback determinístico de sempre, nunca quebra.
- Env opcional: `INTERNAL_JOB_TOKEN` (api-server) — qualquer string aleatória longa, usada só pra autenticar `POST /internal/opportunities/regenerate` (disparo manual do job de regeneração de oportunidades, fora do frontend). Sem ela configurada, o endpoint responde 503.

### Testar pelo celular (mesma rede Wi-Fi)

Os dois servidores já escutam em `0.0.0.0` (todas as interfaces) — não precisa mudar nada no código. Falta só liberar o Firewall do Windows pra aceitar conexão de outros dispositivos, uma vez só, num **PowerShell como Administrador**:

```powershell
New-NetFirewallRule -DisplayName "InvestRadar Dev - Frontend" -Direction Inbound -LocalPort 25214 -Protocol TCP -Action Allow -Profile Private
New-NetFirewallRule -DisplayName "InvestRadar Dev - API" -Direction Inbound -LocalPort 8080 -Protocol TCP -Action Allow -Profile Private
```

Depois, com o celular na mesma rede Wi-Fi, abrir `http://<IP-da-máquina>:25214` (descobrir o IP com `ipconfig`, campo IPv4). O proxy `/api` do Vite roda no servidor, então sessão/cookie funcionam normalmente — não é preciso mexer em CORS.

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Where things live

- `lib/db` — schema Drizzle (users, assets, alerts, opportunities, transactions, analyses, investor_profiles, portfolio_snapshots), fonte de verdade do banco
- `lib/api-spec/openapi.yaml` — fonte de verdade dos contratos de API
- `lib/api-zod`, `lib/api-client-react` — gerados via Orval a partir do OpenAPI (não editar à mão)
- `artifacts/api-server` — backend Express (rotas em `src/routes`)
- `artifacts/carteira` — frontend (páginas em `src/pages`)
- `artifacts/mockup-sandbox` — sandbox de design do Replit, não faz parte do app publicado

## Architecture decisions

- **Alerta de Preço** (`getPriceHistories` em `market-data.ts`, `computePriceAlerts` em `analysis.ts`): usa `?range=3mo&interval=1d` da brapi.dev — testado antes de assumir e confirmado que funciona pra qualquer ticker cotável (ação não-liberada, FII, índice), sem precisar dos `modules` pagos que bloqueiam a análise fundamentalista. Gera 4 alertas por ativo: subiu/caiu ≥8% em 5 pregões (comparando com o fechamento de 5 pontos atrás no histórico diário), e rompimento de máxima/mínima de 52 semanas (`fiftyTwoWeekHigh`/`fiftyTwoWeekLow` do próprio quote) — o spec original pede "máximas históricas"/"mínimas relevantes", aproximado aqui pela janela de 52 semanas por ser a única que a API expõe de graça. Lógica de limiar validada com dados sintéticos (nenhum ativo real bateu ±8% ou tocou o extremo no momento do teste); pipeline de dados real validado ponta a ponta com 6 tickers reais. Ícone do Radar (`preco` → `TrendingDown`) é fixo pro tipo, não muda pra alta/rompimento de topo — simplificação cosmética menor, não corrigida.
- Cotações reais via brapi.dev (`artifacts/api-server/src/lib/market-data.ts`), com cache em memória de 5 min (uma requisição por ticker, em paralelo — ver gotcha abaixo). Cobre `acoes`, `fiis`, `etfs`, `bdrs`; `renda_fixa`/`fundos` não têm ticker de bolsa. O helper compartilhado `getPricesFor(items)` (também exporta `QUOTED_CATEGORIES`) é usado por `assets.ts`, `portfolio.ts` e `opportunities.ts` — não duplicar essa lógica de novo num quarto lugar, importar dali.
- **Os dois "Vender"** (`resolveStatusReason`, `computeTrimSuggestion`): `resolveAnalysisStatus` devolve VENDER por um OU de duas causas que pedem ações opostas — `score < 40` (o problema é o ATIVO) ou posição acima do crítico do perfil (o problema é o TAMANHO, e o ativo pode ter score 90). A palavra sozinha não distinguia, e o usuário não sabia se vendia tudo ou parte. Agora `statusReason` separa as duas e o badge vira **"Reduzir"** (laranja) quando é concentração. Só nesse caso existe quantidade: `X = v − h·T` traz a posição ao limite `high`, **assumindo realocação dentro da carteira** — se o dinheiro sair, o correto seria `X = (v − h·T)/(1 − h)`, quase um terço a mais, e por isso a premissa vai escrita na tela. Quando a causa é fundamento, o card diz explicitamente que não há número calculável em vez de inventar um. O IR é estimado sobre a FATIA vendida, não sobre a posição inteira (a isenção de R$ 20 mil/mês é sobre o valor da venda). **Cuidado ao mexer**: `statusReason`/`trimSuggestion` são recalculados na LEITURA, nunca persistidos — dependem da carteira de agora, e a posição que pesava 45% na geração pode pesar 20% hoje.
- **Alocação-alvo e plano de aporte** (`allocation-engine.ts`, tabela `allocation_policies`, rotas `/portfolio/allocation` e `/portfolio/allocation/plan`): o alvo por classe vem do perfil (renda fixa 80/60/30 por Conservador/Moderado/Arrojado, praxe de mercado) e é editável — a resposta carrega `source` (`personalizado`/`perfil`/`generico`) porque a divisão da parte variável entre ações/FIIs/ETFs é convenção nossa, não dado. O plano de aporte resolve `x_c = max(0, d_c − λ)` sobre as faltas `d_c = alvo_c·(T+aporte) − v_c`, o que minimiza a soma dos quadrados dos desvios: o dinheiro vai primeiro para as classes mais distantes do alvo. **Só compra, nunca vende** — classe acima do alvo não recebe nada e é diluída pelo crescimento. Nada aqui é otimização de carteira: média-variância exigiria retorno esperado, que não temos de fonte real. As sugestões de ticker por classe saem do MESMO ranking da tela de Oportunidades (`opportunity-ranking.ts`, extraído de `routes/opportunities.ts` justamente para não haver duas ordenações divergindo).
- **Posição em Tesouro Direto marcada a mercado** (`treasury-identity.ts`, colunas `assets.treasury_bond_type`/`treasury_maturity_date`): renda fixa pública deixa de ficar congelada no preço de compra. O par (família, vencimento) identifica o título — **não** uma FK para `treasury_bonds.id`, porque aquela tabela é substituída inteira a cada sincronização e os ids não sobrevivem ao dia. Com o par, o `ticker` passa a ser **derivado no servidor** (`canonicalTickerFor`), o que resolve de uma vez identidade e consolidação: antes, "TESOURO IPCA+ 2035" e "TD IPCA 2035" viravam posições distintas do mesmo papel. A marcação usa o **PU de RECOMPRA**, nunca o de compra (spread de até 2,66% nos IPCA+ longos — usar o de compra infla o patrimônio justamente nos títulos de maior prazo), e vai com `priceAsOf` = data-base. Ligado dentro de `getPricesFor`, então patrimônio, distribuição, evolução, saúde, concentração, meta de renda e alocação passaram a contar o Tesouro corretamente sem mudança em cada rota. Renda fixa **privada** (CDB/LCI/LCA) segue texto livre e preço médio: não há fonte pública. Cuidado ao mexer: `pricesStale` no summary exclui título público de propósito — PU datado é o normal ali, e incluí-lo faria o Dashboard alertar "cotação indisponível" todo dia numa carteira saudável.
- **PU do dia da compra** (`priceOnDate`, `GET /treasury/price`): `treasury_bonds` deixou de ser a foto do dia e passou a guardar a série inteira (~175 mil linhas, desde 2004), porque o cadastro precisa do PU **da data em que o usuário comprou**. Pré-preencher com o PU de hoje gravaria um preço médio errado — e errado de forma convincente, que é pior. O formulário pede **data da compra + valor investido** (o que a pessoa sabe) e deriva PU pago e quantidade (o que ela não sabe). A busca é "data-base mais recente ANTERIOR OU IGUAL à pedida", porque compra em fim de semana não tem publicação no dia, e a data usada volta na resposta para a tela poder avisar. Quem quer o "hoje" usa `latestTreasuryBonds()` — sem esse filtro uma consulta traria duas décadas por título. **Gotcha do sync**: a decisão de refazer o backfill olha a contagem de datas-base DISTINTAS, não se há linhas — uma instalação vinda da versão anterior tem exatamente uma data e, olhando só a data máxima, concluiria que está em dia e nunca baixaria o histórico.
- **Renda fixa via Tesouro Direto** (`treasury-data.ts`, `treasury-engine.ts`, tabela `treasury_bonds`): fonte são os dados abertos do Tesouro Nacional (Tesouro Transparente/CKAN, ODbL, sem chave) — o endpoint `tesourodireto.com.br/json/.../treasurybondsinfo.json` que a maioria dos exemplos cita responde **410 Gone**. A URL do CSV é resolvida via `package_show` em vez de fixada, porque muda quando republicam. O arquivo tem ~14 MB/175 mil linhas (histórico desde 2002) e é processado em **streaming**, guardando só a data-base mais recente (~60 linhas) — a ordenação das linhas não é garantida, então não dá para ler só o fim. Três armadilhas registradas no código: (1) a taxa do **Tesouro Selic é ágio/deságio sobre a Selic**, não rendimento — exibida crua, o título mais conservador apareceria rendendo zero, por isso `rateLabelFor` rotula por família; (2) o arquivo **não diz o que está em oferta** (o IGP-M, não emitido há anos, vem com taxa de compra normal), então as famílias sugeríveis são **allowlist explícita**, nunca inferência; (3) o PU do Selic passa de R$ 19 mil, então a tela mostra a **compra mínima** (1% do título, piso de R$ 30 — regra do Tesouro, não campo do arquivo). A escolha do título é determinística sobre o perfil já coletado (liquidez/reserva → Selic, único sem marcação a mercado no resgate; horizonte ≥ 5 anos → IPCA+; abaixo → Prefixado; objetivo `renda` → variante com juros semestrais) e sempre descreve **característica do produto**, nunca previsão de juros.
- **Fallback de cotação** (`price_snapshots`, `getLastKnownPrices`): toda cotação que a brapi.dev devolve de fato é gravada como último preço conhecido do ticker. Quando ela cai, `getPricesFor` desce três degraus — cotação ao vivo → último preço conhecido (até 30 dias) → preço médio de compra — e devolve `PricePoint { price, asOf }`, onde `asOf != null` marca a defasagem. Quem exibe o número ao usuário é obrigado a mostrar a data: `Asset.priceAsOf` na carteira, `PortfolioSummary.pricesStale` no dashboard. `getQuotes` continua devolvendo só dado ao vivo de propósito — fundamentos e alerta de preço não podem ser calculados sobre preço datado.
- **Setor real** (`Fundamentals.sector`, via `?modules=summaryProfile` na mesma chamada de `fetchKeyStatistics`): prioridade é setor manual do usuário > setor real da brapi.dev (português, ex: "Energia", "Bens Industriais") > `SECTOR_MAP` curado (fallback pra renda_fixa/fundos e falha pontual) > "Outros". Usado em `sectorFor()`, chamada com o `Fundamentals` map de `getFundamentals()` como segundo argumento em `/portfolio/distribution`, `/portfolio/health` e nos alertas de concentração.
- **Dividendos reais** (`getDividendEvents()` em `market-data.ts`): `POST /analysis/generate` calcula `totalDividends`/`portfolioYield` de verdade (trailing 12 meses × quantidade atual detida) via `/api/v2/stocks/dividends` (ações/BDRs, em lote, confiável) e `/api/v2/fii/dividends` (FIIs **e ETFs**, best-effort por ticker). ETFs entram no caminho de FII, não no lote de ações — testado e confirmado que a brapi.dev rejeita o lote INTEIRO de `/v2/stocks/dividends` com `FII_DIVIDENDS_MISUSE` quando qualquer ticker de sufixo "11" (todo ETF B3) entra na mesma chamada, derrubando silenciosamente o dado real de ações que estariam no mesmo lote de até 10 — bug real encontrado e corrigido (antes, ter um ETF na carteira podia zerar o dividendTrend de ações reais no mesmo lote). `/api/v2/fii/dividends` é `FEATURE_NOT_AVAILABLE` pra ETF no plano atual (confirmado), então o ETF fica sem histórico real mesmo — isolado, não contamina mais o resto do lote.
- **Payout ratio** (`evalPayoutRatio` em `analysis-engine.ts`): DPS real dos últimos 12 meses (`sumLast12Months`, market-data.ts) dividido por EPS (`price / priceEarnings`, já real) — só ações (FII não tem P/L real disponível no plano atual, `financialData`/`incomeStatementHistory`/`balanceSheetHistory` todos vazios ou 403 pra FII, testado). ≤60% saudável, 60-100% neutro, >100% risco explícito ("distribui mais do que lucra"); P/L negativo com provento pago no período é o pior caso (prejuízo distribuindo). Entra na média de `analyzeFundamentals` como mais um fundamento — Parecer de Ativo, Radar por ativo e `opportunities-engine.ts` (universo inteiro) todos avaliam. `sumLast12Months`, não `computeDividendTrend` — só a janela de 12 meses importa aqui, exigir 24 meses (como a comparação de tendência exige) descartaria dado real de ativos cujo provider só cobre ~12 meses (comum em FII).
- **Renda passiva projetada** (`GET /portfolio/dividends/projection`, página `dividendos.tsx`): projeta renda anual/mensal a partir de DPS real dos últimos 12 meses (`sumLast12Months`) × quantidade atual — não o `dividendYield` agregado do provider. `byAsset` traz DY-on-price e DY-on-cost (sobre `averagePrice`) por ativo; `byMonth` é a distribuição REAL de quando os proventos caíram no ano, útil pra ver se a carteira está concentrada em poucos meses. Ativo sem histórico suficiente entra com `dps12m: null` e não soma na projeção — nunca estimado via atalho. Sem migração (calculado ao vivo, igual à consolidação mensal de IR de vendas).
- **Saúde do Portfólio** (`/portfolio/health`, página `saude.tsx`): com 0 ativos retorna todas as dimensões zeradas (`score: 0`) em vez dos fallbacks de "sem ações na carteira" (era um bug: carteira vazia mostrava Score 34, Risco 80, Dividendos 50, Crescimento 68 — os mesmos fallbacks usados pra carteira só-renda-fixa). O frontend usa `assetCount` de `/portfolio/summary` pra decidir entre o card de score e o estado "Diagnóstico Indisponível" que já existia mas nunca era acionado. Com ativos reais, `risk`/`dividends`/`growth` agora são médias ponderadas pelo valor de cada posição usando `evalVolatility`/`evalDividendYield`/`evalRevenueGrowth` (mesmos buckets do motor de análise), reaproveitando `getFundamentals()`; ativo sem dado real disponível simplesmente não pesa nessa dimensão. `aiDiagnosis` (campo novo, nullable) é um diagnóstico qualitativo via Claude Haiku por cima do score já calculado (`portfolio-ai.ts`) — null sem `ANTHROPIC_API_KEY`, nunca recalcula o score.
- **Histórico de patrimônio** (`portfolio_snapshots`, `artifacts/api-server/src/lib/portfolio-history.ts`): 1 linha por usuário por dia (upsert por `userId`+`date`), gravada toda vez que `/portfolio/summary` é chamado — sem cron, sem job agendado, o histórico real cresce sozinho só de o usuário usar o app no dia a dia. `/portfolio/evolution` e `/portfolio/benchmarks` usam o snapshot real do mês quando existe; meses sem snapshot ainda caem no fallback simulado de antes (o real vai ocupando o lugar do simulado com o tempo, nunca o contrário). Carteira vazia mostra 0% reto, não ganho fabricado (esse era um bug: `/portfolio/benchmarks` nunca consultava os ativos do usuário, era só `Math.random()`).
- **CDI/IBOV/IFIX reais** (`artifacts/api-server/src/lib/benchmark-data.ts`, tabela global `index_snapshots`): CDI é 100% real pros 12 meses sempre — série 4390 do SGS/BCB já retorna o retorno acumulado do mês em %, sem custo, com anos de histórico disponível, então não precisa de tabela nem de fallback simulado (validado ponto a ponto contra o cálculo manual). IBOV/IFIX não têm esse luxo: `?range=3mo&interval=1d` da brapi.dev dá histórico diário real só pro IBOV (~3 meses, testado e confirmado); o mesmo parâmetro no IFIX devolve só o candle de hoje (sem histórico algum no plano grátis) — testado antes de assumir que funcionaria igual. Por isso o IBOV já nasce com ~3 meses reais retroativos (backfill automático na primeira chamada), e o IFIX só acumula 1 dia por vez a partir de agora, igual ao padrão de `portfolio_snapshots`: snapshot diário salvo em `index_snapshots` (upsert por `indexName`+`date`, tabela global, não por usuário) a cada chamada de `/portfolio/benchmarks`; meses sem 2 fechamentos consecutivos no banco caem no fallback simulado de sempre (real substitui simulado com o tempo, nunca o contrário, mesma regra do histórico de patrimônio).
- Motor de análise (`artifacts/api-server/src/lib/analysis-engine.ts`) é **regras determinísticas**, não IA/LLM. `analyzeFundamentals()` é chamada de verdade por `computeAnalysis()` em `routes/analysis.ts`, alimentada por `getFundamentals()` (`market-data.ts`). O módulo pago `financialData` da brapi.dev (que traria ROE/dívida-patrimônio/crescimento prontos) não está disponível no plano atual — testado: pedir `financialData` junto de outro módulo na mesma chamada derruba a chamada **inteira** com 403 `MODULES_NOT_AVAILABLE`, não só o campo que falta. Por isso `fetchKeyStatistics` pede só `?modules=defaultKeyStatistics` (P/L, P/VP, DY, beta, margem líquida — real, disponível), e ROE/dívida-patrimônio/crescimento de receita são **calculados** a partir do balanço e DRE reais via os endpoints v2 (`GET /api/v2/stocks/balance-sheet` e `/income-statement`, `?symbols=A,B,C` — diferente do v1, aceita vários tickers numa chamada só, dado no padrão CVM): ROE = `netIncome / shareholdersEquity`, dívida/patrimônio = `(loansAndFinancing + longTermLoansAndFinancing) / shareholdersEquity`, crescimento = receita do ano mais recente vs anterior. Ticker sem fundamentos disponíveis (falha pontual do provider) cai em `pendingAnalysis()` (`available: false`) — nunca um score inventado. Categorias sem ticker (`renda_fixa`/`fundos`) usam `analysisForUnquotedAsset()` — esse caso é `available: true`, é uma limitação estrutural (não tem o que analisar), não uma pendência de dados. Frontend (`analise.tsx`, coluna "Status" em `carteira.tsx`) mostra badge "Em breve" quando `available === false`, sem fingir um score.
- **IR estimado por posição** (`tax-engine.ts`, `estimateCapitalGainsTax()`): calculado só em `POST /analysis/generate` (precisa do preço atual) pra ações/FIIs/ETFs/BDRs — ações isentas até R$20 mil vendidos no mês, 15% acima disso; FIIs sempre 20%, sem isenção; ETFs/BDRs 15% sem isenção. É uma **estimativa isolada**: assume ser a única venda de renda variável do usuário no mês, já que o app não guarda histórico de vendas (sem isso não dá pra saber se a isenção mensal já foi usada por outra venda, nem se há prejuízo acumulado a compensar) — documentado explicitamente como não sendo o valor exato que a Receita cobraria. Exposto como `taxEstimate` em `AssetAnalysis` (null pra renda_fixa/fundos ou fora do POST /generate) e alimenta o prompt de `analysis-ai.ts`: por decisão explícita do usuário, a IA pode dizer diretamente que vale considerar reduzir/encerrar uma posição quando os fundamentos justificarem (deixou de ser só "observe"), pesando o custo de IR como contra-argumento — score/status continuam 100% do motor determinístico, a IA nunca os toca.
- Autenticação por sessão (`express-session`, cookie httpOnly), sem distinção de perfis, conforme o prompt original.
- Perfil de investidor (`/profile`, `investor_profiles`) é **opcional** — preenchido em Configurações, não no cadastro. Score 0-100 somado a partir de 5 perguntas (20 pts cada), classificação Conservador (<34) / Moderado (34-66) / Arrojado (≥67).
- `opportunities` é regenerada automaticamente a cada semana (`lib/scheduler.ts` + `lib/opportunities-engine.ts`), varrendo um universo buscado ao vivo em `GET /api/quote/list` (`lib/ticker-universe.ts`, `fetchTickerUniverse()` — top 80 ações/50 FIIs/15 ETFs/25 BDRs por market cap, filtrando tickers do mercado fracionário tipo `PETR4F`) com fundamentos reais e o mesmo `analyzeFundamentals()` usado por ativo — só entra quem bate `score >= 60`. Universo vazio (provider fora do ar) aborta o job sem mexer na tabela existente, em vez de esvaziá-la. `riskLevel` é determinístico (buckets de `evalVolatility`); `potentialReturn` não tem fonte de dado real disponível (o módulo `financial-data` com preço-alvo de analista dá 403 no plano atual), então é uma heurística documentada em cima de score+dividendYield, não um número inventado. `reason`/`positives`/`risks`/`horizon` são reescritos por Claude (`opportunities-ai.ts`) a partir dos números já calculados, com validação de JSON e fallback pro texto determinístico do analysis-engine em qualquer falha. Scheduler in-process (checa de hora em hora, persiste `lastRunAt` em `job_runs` — sobrevive a restart do Railway sem redisparo duplicado). Disparo manual: `POST /internal/opportunities/regenerate` com header `Authorization: Bearer $INTERNAL_JOB_TOKEN`. `scripts/src/seed-opportunities.ts` continua existindo como bootstrap manual (banco novo, sem token configurado em dev). `/opportunities` reordena o Top 10 pelo `riskLevel` compatível com a classificação do perfil do usuário (Conservador prioriza risco Baixo, Arrojado prioriza Alto); sem perfil definido, mantém a ordenação simples por score. `currentPrice` é buscado só pros 10 já rankeados (cotação real, mesmo cache de `market-data.ts`).
- brapi.dev v2 (`GET /api/v2/stocks/balance-sheet`, `/income-statement`, `?symbols=A,B,C`): balanço/DRE reais padrão CVM, mas limitado a 10 tickers por requisição no plano atual (`QUOTES_PER_REQUEST_EXCEEDED` acima disso, sem `results`) — `fetchV2Statements` em `market-data.ts` faz o chunking em lotes de 10 em paralelo. Alguns tickers mudaram de código por evento societário e só resolvem pelo código novo: ELET3→AXIA3, EMBR3→EMBJ3, JBSS3→JBSS32.
- Navegação mobile (`app-layout.tsx`, abaixo de `md`): barra superior com hambúrguer (abre o drawer com todos os itens) + barra inferior fixa com os 5 destinos mais usados (Início, Carteira, Radar, Análise, Oportunidades). Dividendos/Saúde/Configurações ficam só no drawer. Desktop usa a sidebar fixa de sempre, sem nenhuma das duas barras.
- Minha Carteira (`carteira.tsx`) é responsiva: tabela de 9 colunas no desktop (`hidden md:block`), cards empilhados no mobile (`md:hidden`) — a tabela sozinha forçava rolagem horizontal em telas estreitas. Os dois blocos renderizam a partir da mesma lista de `assets`, então qualquer campo novo precisa ser adicionado nos dois lugares.
- **Macro** (`artifacts/api-server/src/lib/macro-data.ts`): Selic, IPCA (12m) e câmbio via API pública do Banco Central (SGS), sem chave, cache de 6h. `/dados/ultimos/N` do SGS tem limite de 20 pontos — pra tendência da Selic (janela de ~6 meses) usar `/dados?dataInicial=...&dataFinal=...` em vez disso. Exibido num painel no topo do Radar Inteligente. `/analysis/generate` gera alerta `macroeconomico` quando IPCA 12m > 4,5% ou Selic em trajetória de alta.
- **Alerta de concentração** (`computeConcentrationAlerts` em `analysis.ts`, chamado por `/analysis/generate`): não depende de nenhuma fonte de dados nova, só reusa preço (`getPricesFor`) e setor (`sectorFor`, movido de `portfolio.ts` pra `market-data.ts` pra não duplicar) já calculados. Três regras: ativo único ≥40% do patrimônio = `Critico`, ≥25% = `Alto`; setor único ≥50% = `Alto`; menos de 3 ativos distintos = `Medio` ("baixa diversificação"). Gera alerta tipo `concentracao` (enum já existia no OpenAPI, nunca tinha sido usado). Validado direto contra o Supabase de produção com um usuário de teste (100% em 1 ativo → Critico; diluído pra ~27%/73% → Alto/Critico corretos), dados de teste removidos depois.
- **Notícias** (`artifacts/api-server/src/lib/news.ts`): busca via RSS de busca nativo do WordPress do InfoMoney (`?feed=rss2&s=termo`) — não usar o feed geral (`/feed/`), ele só tem ~10 itens no total e raramente menciona uma empresa específica; a busca por nome já traz resultado direto. O termo de busca é o nome popular da empresa pros tickers mais negociados (`COMPANY_ALIASES`: Petrobras, Itaú, Bradesco etc., onde nome popular ≠ nome legal da brapi.dev); fora da lista, usa o **próprio ticker** como termo de busca — usava a primeira palavra do nome legal antes, mas isso gerou um falso positivo real em produção (MXRF11 = "Maxi Renda Fundo de Investimento Imobiliario", buscar só "Maxi" trouxe propaganda de carrinho de bebê "Maxi Baby"; testando outros FIIs, HSRE11="HSI" trazia notícia sobre imigração nos EUA). Buscar pelo ticker é mais seguro E pelo menos tão preciso nos testes (InfoMoney cobre FIIs citando o ticker explicitamente: "FII MXRF11 divulga...") — validado contra MXRF11/XPML11/HSRE11 (sem mais falsos positivos) e re-testado nos tickers já aliados (PETR4, VALE3, WEGE3 etc., sem regressão). Classificação de impacto via Claude Haiku (`classifyImpact`, cacheada 24h por manchete) — sem `ANTHROPIC_API_KEY`, mostra a manchete real sem classificação, nunca inventa impacto. Notícia negativa/muito negativa em ativo da carteira gera alerta tipo `noticias`. `XMLParser` precisa de `{ htmlEntities: true }`, senão entidades como `&#8220;` aparecem cruas no título.

- Frontend: https://invest-radar-carteira.vercel.app
- API: https://invest-radar-production.up.railway.app (não é pra usuário final acessar direto — sempre pelo domínio da Vercel, que faz proxy de `/api/*` pra cá)
- Banco: Supabase, projeto `gzqqwpetlfruokgnfmzp`, connection string do pooler (modo *transaction*, porta 6543) guardada como `DATABASE_URL` no Railway

Arquitetura: a Vercel faz *rewrite* de `/api/*` pro domínio do Railway (`artifacts/carteira/vercel.json`) — o navegador nunca vê dois domínios diferentes, então sessão/cookie funcionam exatamente como em dev local (proxy do Vite) e não precisou mexer em CORS nem em `sameSite`. Não confundir com a arquitetura serverless da Vercel — o api-server continua sendo um processo Node tradicional no Railway, só o frontend estático vai pra Vercel.

**Pra reproduzir do zero** (ex: outro ambiente, staging):

1. **Supabase**: criar projeto → pegar connection string do pooler (Settings → Database → Connect → Transaction pooler) → rodar `DATABASE_URL="<string>" pnpm --filter @workspace/db run push` e depois `pnpm --filter @workspace/scripts run seed-opportunities` apontando pra ela
2. **Railway**: "Deploy from GitHub repo" — **raiz do repo como root directory**, não `artifacts/api-server` (o pnpm workspace precisa do repo inteiro pra resolver os pacotes `@workspace/*`). Se ele auto-detectar o monorepo e criar um serviço por pacote (`@workspace/carteira`, `@workspace/api-spec` etc.), **apague todos exceto um** e configure esse com root directory vazio — só assim ele usa o `railway.json` da raiz. Env vars: `DATABASE_URL`, `SESSION_SECRET`, `BRAPI_TOKEN`, `ANTHROPIC_API_KEY`, `INTERNAL_JOB_TOKEN`, `NODE_ENV=production` (`PORT` é automático). Gerar o domínio em Settings → Networking → Generate Domain.
3. **Vercel**: import project, **Root Directory = `artifacts/carteira`**, env var `BASE_PATH=/` (obrigatória, ver gotcha — sem ela o build falha). Editar `artifacts/carteira/vercel.json` trocando o domínio do rewrite pelo domínio real do Railway antes do deploy.

Depois do primeiro deploy dos três, testar cadastro/login/navegação pelo domínio da Vercel antes de considerar concluído — foi assim que os três gotchas abaixo (pnpm 11, cookie de sessão, rotas 404) apareceram.

## Gotchas

- **Windows dev**: `pnpm-workspace.yaml` tinha overrides que zeravam os binários nativos não-Linux de `esbuild`, `rollup`, `lightningcss` e `@tailwindcss/oxide` (comentário original: "replit uses linux-x64 only"). Já removidas as entradas `win32-*` — se voltar a quebrar após um `pnpm install`, comece por aí.
- **Git Bash / MSYS no Windows**: `BASE_PATH=/` é reescrito para o path do Git (`/Program Files/Git/...`) pelo MSYS. Rode com `MSYS_NO_PATHCONV=1` na frente do comando.
- O script `dev` do `api-server` usava `export NODE_ENV=...` (sintaxe bash), que quebra no shell padrão do pnpm no Windows (cmd.exe). Já corrigido — `NODE_ENV` não é obrigatório, só é comparado com `"production"` em `app.ts`/`logger.ts`.
- `lib/db/drizzle.config.ts` usava `path.join(__dirname, ...)`, que gerava um path com `\` no Windows e o drizzle-kit não encontrava o schema. Trocado para path relativo simples.
- **brapi.dev**: os planos free/free-token permitem só **1 ticker por requisição**. `market-data.ts` faz uma requisição por ticker (em paralelo) — nunca volte a agrupar tickers numa chamada só (`/quote/A,B,C`), a API rejeita a lista inteira e derruba o preço de todos os ativos daquele lote, não só do que causou o problema.
- `vite.config.ts` da carteira exigia `PORT` mesmo pra `vite build` (que não abre porta nenhuma) — isso quebraria todo build na Vercel. Corrigido: `PORT` só é exigido quando `command === 'serve'` (dev/preview). `BASE_PATH` continua sempre obrigatório (afeta os paths dos assets no HTML gerado, isso sim importa pro build) — configurar como env var na Vercel.
- **Railway/Nixpacks não suporta pnpm 11** — trata como v9 desconhecida e quebra com um erro enganoso (`ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING`, sem nenhuma relação óbvia com versão de pnpm). `package.json` está fixado em `pnpm@10.34.5` por causa disso — não subir pra 11.x sem checar se o Nixpacks já suporta.
- **Cookie de sessão não era definido em produção** (login retornava 200 mas sem `Set-Cookie`): Railway/Vercel terminam TLS antes da requisição chegar no processo Node, e sem `app.set("trust proxy", 1)` o Express não confia no `X-Forwarded-Proto`, então `req.secure` fica `false` e o `express-session` recusa definir um cookie `secure: true` (não é só a flag, ele nem tenta). Já corrigido em `app.ts` — se voltar a acontecer num novo ambiente atrás de proxy, é o primeiro lugar pra olhar.
- **Rotas client-side davam 404 na Vercel** (`/login`, `/carteira` etc. só existem no React Router, não são arquivos): faltava um rewrite catch-all pro `index.html` em `vercel.json`, depois do rewrite de `/api/*` (ordem importa, primeiro match vence).
- **Merge em `main` não garante deploy.** Railway e Vercel disparam por evento de git, e o evento pode se perder ou falhar sem que nada apareça no GitHub — nenhum dos dois publica status no commit, então a PR fica verde e o código continua não sendo publicado. Como diagnosticar sem acesso aos painéis:
  - *Backend*: pedir uma rota que só existe no código novo. **404 significa build antigo no ar**; 401 significa que a rota existe e o deploy chegou (comparar sempre com uma rota antiga protegida, que deve dar 401 nos dois casos).
  - *Frontend*: comparar o hash do bundle servido (`curl -s <url> | grep -o 'assets/index-[A-Za-z0-9_-]*\.js'`) com o de um `BASE_PATH=/ vite build` local no mesmo commit. Hash diferente = a Vercel não publicou esse commit.
  - Antes de suspeitar do código, rodar os dois builds de produção localmente — se passam, o problema é de plataforma.
  - As duas falhas exigem tratamentos diferentes: se o host **tem** registro do deploy e ele falhou, "Redeploy" resolve; se **não tem registro nenhum** (evento perdido), Redeploy só reexecuta o deploy anterior, com o código velho — nesse caso o único caminho é um commit novo em `main`, que gera um evento novo.
